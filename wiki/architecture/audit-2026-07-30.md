# Code Audit — 2026-07-30

Snapshot taken after a test-coverage expansion pass. This is a candid
assessment, not a marketing piece. Items are ordered by severity within
each section.

## TL;DR

- **36 new tests added**, total 194 tests pass (was 158).
- Several heavily-used modules jumped from 0% to full coverage
  (`JobSearchTool`, `MarkdownFetchTool`, `WebSearchTool`, `Constants`).
- The audit found **8 high-severity correctness issues**, several
  design-level dead code, and a handful of architectural smells. None
  are security vulnerabilities; all are robustness or maintainability.

## Correctness findings

### High severity

**1. `JobSearchAgent.cs:141` — synchronous LLM call in async method**
`CompleteChat(messages, options, cancellationToken)` is the *blocking*
OpenAI client method. `JobEvaluationAgent` (line 77) uses the proper
`CompleteChatAsync`. Pick one and use it everywhere. In a console
process with a local LLM this is cosmetic, but it sets a bad example
and would deadlock under a sync-over-async scenario.

**2. `JobSearchAgent.cs:146` — broken content-length calculation**
`messages.Select(m => m.Content.ToString())` is wrong: `ChatMessage.Content`
is `IList<ChatMessageContentPart>`, so `.ToString()` returns the type
name, not the rendered text. The "Total content length" log line is
meaningless. Use `m.Content.Select(p => p.Text).Sum(t => t?.Length ?? 0)`
or a similar accumulator over the actual text parts.

**3. `JobRepository.SaveAsync` — TOCTOU race on uniqueness**
The check-then-insert pattern (lines 27-38) is not protected by any
unique constraint on `(Email, EmployerJobId)`. Two concurrent
`SaveAsync` calls for the same job can both pass the existence check
and both insert. The mitigation is either:
- add a composite index with `IsUnique = true` in the EF model, or
- wrap in a try/catch on `DbUpdateException` and look up the existing row.

`IsUnique` is the cleaner fix. Currently no index at all exists on
this combination.

**4. `JobsService.GetJobsAsync` — full materialization + in-memory paging**
`QueryAsync` returns the entire result set, then the service filters,
sorts, and pages in C# (lines 65-116). For a tenant with thousands of
ingested jobs, every request loads the full list, sorts it, and
discards most rows. Push the paging down to the database with `Skip` /
`Take` inside `QueryAsync`, or add a new method that takes `page` and
`pageSize`.

**5. `Fidalgo.Host/Program.cs:60-79` — unhandled exceptions in resume API**
`/api/jobs/{id:guid}/resume` calls `chatClient.CompleteChatAsync` and
indexes into `completion.Value.Content[0].Text` with no try/catch and
no length check. If the LLM returns no content (refusal, network
error, content filter) the endpoint throws an unhandled exception
that the user sees as a 500. Wrap in a `try/catch` that returns a
proper `Problem(...)` response, and handle the empty-content case
explicitly.

**6. `Fidalgo.Host/Program.cs:92-95` — auto-launch uses `cmd` with empty catch**
```csharp
Process.Start(new ProcessStartInfo("cmd", $"/c start {url}") { CreateNoWindow = true });
```
Two issues: (a) the `url` string is interpolated into a command line
without escaping — if `app.Urls` ever contains spaces, quotes, or
`&`/`|` characters this breaks or, worse, runs injected commands; (b)
the `catch { }` block at line 94 silently swallows any launch
failure, making debugging hard. Use `Process.Start(new ProcessStartInfo(url)
{ UseShellExecute = true })` which is the cross-platform idiomatic way
to open a URL, and at least log the swallowed exception.

**7. `HtmlSanitizer` is dead code**
204 lines, registered in DI in both `Fidalgo.Agent` and
`Fidalgo.Ingest`, but no consumer anywhere in the production code
(verified by full-text search). The actual HTML sanitization in
production uses `HtmlStripper` (HtmlAgilityPack). Either:
- delete `HtmlSanitizer.cs` and the two `AddScoped<HtmlSanitizer>()`
  registrations, or
- if a future feature needs the AngleSharp variant, mark it `[Obsolete]`
  with a clear migration note and don't register it in DI yet.

**8. `IRetryPolicy` and `IExceptionMapper` are registered but never used**
Both are registered as singletons in both `Program.cs` files, neither
is injected anywhere. They have 100%-tested implementations and 100%-tested
behaviour, but zero callers. This is a real design smell:
- Either wrap the LLM/HTTP calls with `IRetryPolicy.ExecuteAsync` to
  actually do retries on transient failures, and use `IExceptionMapper`
  in the global exception middleware of the Host to map
  `ValidationException`/`NotFoundException`/`UnauthorizedException` to
  proper HTTP responses, or
- delete the registrations and the interfaces if the
  "transient-failure handling" and "structured error responses" are
  not in scope.

Currently `Services/JobsService` re-implements exception wrapping
inline (`throw new InvalidOperationException("Failed to load jobs...",
ex)`) — which is exactly the job `IExceptionMapper` exists to do.

### Medium severity

**9. `JobSearchAgent.cs:269` — `NotImplementedException` for unknown tools**
If the LLM hallucinates a tool name, the exception bubbles up, breaks
the agent loop, and the user sees a crash. Return a structured
`ToolChatMessage` with an error string so the LLM can self-correct:
```csharp
return $"Unknown tool '{toolCall.FunctionName}'. Available: ...";
```

**10. `JobSearchAgent` tool-argument parsing is fragile**
`GetProperty("url")` on line 200, 237, 248, 255, etc. throws
`KeyNotFoundException` if the LLM omits a required field. The `catch`
in the outer agent loop (lines 139-148) only handles 400 Bad Request
from the LLM, not parse failures. Wrap each `GetProperty` in a
`TryGetProperty` and return a clear error message to the LLM when the
arguments are missing or malformed.

**11. `JobSearchAgent.cs:56` — `ILogger<JobSearchAgent> logger = null!`**
The default parameter is `null!` (null-forgiving). The other agent
(`JobEvaluationAgent`) does not have this. If DI ever fails to provide
a logger, this becomes a runtime NRE. Either drop the default and
require the parameter, or default to `NullLogger<JobSearchAgent>.Instance`.

**12. `ApiModeRunner.cs:53` — locale-dependent `DateTime.TryParse`**
```csharp
DateTime.TryParse(job.Created, out var postedDate);
```
Without `CultureInfo.InvariantCulture` and `DateTimeStyles.AssumeUniversal`,
parsing differs across systems and the resulting `DateTime` is `Kind.Unspecified`.
Use `DateTime.TryParse(job.Created, CultureInfo.InvariantCulture,
DateTimeStyles.AssumeUniversal | DateTimeStyles.AdjustToUniversal, out var postedDate)`.

**13. `ApiModeRunner.cs:34-37` — backwards rate limiter**
```csharp
if (page > 1) { await Task.Delay(1000); }
```
This only delays AFTER the first page. The first request goes out
immediately, then the second waits 1s. The Adzuna docs recommend one
request per second; the loop should delay BEFORE every call (or at
least before the first). Also, the 1s is a magic number — make it
configurable.

**14. `ApiModeRunner.cs:75` — hardcoded `20` for page size**
The loop terminates when `jobs.Results.Count < 20`. The Adzuna API
may return variable counts; if it returns exactly 20 on a final page
the loop fetches one extra empty page. Use `jobs.Count` (total) or
`jobs.To` (end index) to decide whether to continue.

**15. `ApiModeRunner.cs:40` — `null` from `SearchRawAsync` is ambiguous**
`SearchRawAsync` returns `null` both when the API returned an error
and when the result list was empty. The loop breaks either way, which
means a transient network error on page 5 silently ends the run. The
return value should distinguish "no more results" from "error".

**16. `JobSearchTool.cs:153-156` — `contractType` silently drops values**
The docstring claims "permanent, contract, internship, trainee" are
supported. The implementation only handles "contract" and "permanent".
`trainee` and `internship` are silently dropped from the query. Either
add them or correct the docstring.

**17. `JobSearchTool.cs:161-165` — fragile `contractTime` normalization**
`ToLowerInvariant().Replace("-", "_").Replace(" ", "_")` followed by
`Contains` is heuristic. `contractTime="full"` matches both `full_time`
and `part_time` (because `full_time`.Contains("full") is true, but
`part_time`.Contains("full") is also true). Use an exact normalized
match instead:
```csharp
var normalized = contractTime.ToLowerInvariant()
    .Replace("-", "_").Replace(" ", "_");
if (normalized == "full_time") queryParts.Add("full_time=1");
else if (normalized == "part_time") queryParts.Add("part_time=1");
```

**18. `JobsService.GetUrl` — null-deref latent**
`j.SourceWebsite.StartsWith("http")` is safe today because
`JobEntity.SourceWebsite` defaults to `string.Empty`, but the contract
isn't enforced. Mark `JobEntity.SourceWebsite` as `required` or guard
the call.

**19. `Fidalgo.Host/Program.cs:34` — pageSize no upper bound at API level**
The service validates 1-100 (line 53), but if a future change moves
the validation to the API, the contract is unenforced at the entry
point. Add `[Range(1, 100)]` on the route parameter or validate in
the minimal-API filter.

**20. `Fidalgo.Host/Program.cs:77` — no timeout on the LLM call**
A stalled LLM (network hang, slow GPU) ties up a request thread
indefinitely. Pass a `CancellationToken` with a timeout, e.g.
`CancellationTokenSource(TimeSpan.FromMinutes(2))`.

**21. `OtlpExporter` is a stub**
Returns `true` and does nothing. The architecture summary claims
"tracing data is exported to OpenTelemetry-compatible collectors";
in practice tracing is generated, captured into `Span` objects, and
then dropped on the floor. Either implement the OTLP gRPC/HTTP push
or document the limitation.

### Low severity

**22. `JobRepository.QueryAsync` line 102** — `PostedDate ?? DateTime.MinValue`
for ordering pushes nulls to the bottom of a descending order. A
comment explaining this would help, or a `coalesce` in SQL.

**23. `JobRepository.ExistsAsync` lines 144-145** — `ToLower()` comparison
should use `string.Equals(..., StringComparison.OrdinalIgnoreCase)` for
clarity.

**24. `JobsService.GetJobsAsync` line 66-67** — hardcoded recommendation
filter ("Maybe" / "Do not apply") isn't documented in the service's
XML doc. The doc says "Retrieves a page of non-deleted jobs" but
actually filters by recommendation too. Make it a parameter or
document it.

**25. `Fidalgo.Host/Program.cs:60`** — `[FromBody]` is imported but the
request is in the body. Functionally correct, but a code comment or
the OpenAPI annotation would help readability.

## Architectural findings

### Dead code / over-DI

- **`HtmlSanitizer`** — 204 lines, registered, never consumed. Delete.
- **`IRetryPolicy` / `IExceptionMapper`** — registered, never consumed
  anywhere. Either wire them up to actual call sites, or remove the
  DI plumbing.

### Inconsistent conventions

- **Async/await**: `JobSearchAgent` uses `CompleteChat` (sync);
  `JobEvaluationAgent` uses `CompleteChatAsync`. Pick one.
- **Logger null-forgiveness**: `JobSearchAgent` has
  `ILogger<...> logger = null!`; the other agent doesn't. Make
  non-nullable the project standard and let DI supply it.
- **DI registration**: `Fidalgo.Agent/DependencyInjection` and
  `Fidalgo.Ingest/DependencyInjection` are 90% identical (HttpClient,
  Adzuna, BrowserFetchOptions, etc.). A shared
  `Fidalgo.Shared/DependencyInjection/AddSharedServices(...)` would
  eliminate the duplication.

### Testability

- **Top-level `Program.cs` files** (`Fidalgo.Agent/Program.cs`,
  `Fidalgo.Ingest/Program.cs`) are top-level statements, not a class
  with a `Main` method. They can't be unit-tested. The `--help`,
  `--QueryJobs`, and `--DiscardJobId` dispatch logic would benefit
  from being moved into a class with a method that takes `args` and
  returns an exit code; the top-level file becomes a one-liner that
  calls it.
- **`JobSearchAgent` and `JobEvaluationAgent` depend on concrete
  `ChatClient`** from the OpenAI SDK. There's no `IChatClient`
  abstraction. Tests can't verify the prompt-assembly logic without
  mocking the entire SDK. A small wrapper interface would unlock
  unit tests for the LLM call sequencing.
- **Long constructor parameter lists**: `JobSearchAgent` (11 params),
  `JobEvaluationAgent` (7 params), `BrowserFetchTool` (3 with
  settings pulled from config). A `JobEvaluationOptions` /
  `JobSearchOptions` record would group related fields and make
  tests simpler.

### Duplication

- **EF migrations are duplicated** byte-for-byte between
  `Fidalgo.Agent/Storage/Migrations` and
  `Fidalgo.Ingest/Storage/Migrations`. Migrations should live in
  `Fidalgo.Shared` so both projects use the same schema and there is
  one source of truth.
- **Prompt construction** is split between
  `Fidalgo.Ingest/Prompts/AgentPrompt.cs` (file read + token
  substitution) and the inline `$@""` literal in
  `JobEvaluationAgent.BuildPrompt`. No central template registry;
  changes to "how the system talks to the LLM" require edits in
  both places.

### In-memory pagination

`JobsService` loads the full result set, sorts in C#, and pages in
memory. See correctness finding #4.

### Tracing

`Span`/`SpanEvent`/`SpanLink` types and `SpanFactory` exist and are
DI-registered, but `OtlpExporter` is a stub. Either implement the
exporter or remove the tracing infrastructure to reduce dead code.

## What I did NOT look at

- Frontend (`Fidalgo.Frontend` / React / Vite). Coverage scope was
  the .NET side.
- Performance under load.
- Dependency version pinning across the 4 test projects (some use
  `Moq`, some use `NSubstitute`, AGENTS.md says NSubstitute — the
  new tests follow NSubstitute, the pre-existing `SaveJobToolTests`
  still uses Moq; not worth a separate PR).
- Security of the resume `/api/jobs/{id}/resume` endpoint
  (no auth). The architecture summary acknowledges this is a known
  gap.

## Suggested next steps (rough priority)

1. Delete `HtmlSanitizer` and unused DI registrations.
2. Wire up `IExceptionMapper` in the Host's global exception
   middleware — small, high value, unblocks HTTP 4xx mapping.
3. Fix `JobsService` pagination at the DB level.
4. Add a unique index on `(Email, EmployerJobId)` in the JobEntity.
5. Fix `JobSearchAgent`'s `CompleteChat`/`Content.ToString` issues.
6. Either implement `OtlpExporter` or remove the tracing abstractions.
7. Hoist EF migrations to `Fidalgo.Shared`.
8. Extract an `IChatClient` abstraction so agent tests can verify
   the LLM call sequence without the OpenAI SDK.
